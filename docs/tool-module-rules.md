# Tool Module Rules

## Definition

A **tool module** implements an integration's operations. It owns its logic, configuration, contracts, commands, and endpoints. Code identifier: `tool_module`.

The module does not know the manager or control its execution. The manager configures, initializes, and exposes it.

## Rules

### 1. Dependencies

Modules do not depend on other modules, the manager, or their consumers.

Prefer the standard library where appropriate.

External dependencies must be necessary, well-known, and trustworthy.

### 2. Self-contained modules

Each module maintains its logic, configuration, contracts, commands, endpoints, and tests. Integration-specific behavior belongs to the module.

### 3. Shared logic for CLI and HTTP

Both interfaces use the same logic without duplication:

- CLI: `ggets <tool-module> ...`
- HTTP: `/<tool-module>/...`

Operation inputs and outputs use JSON in both interfaces.

### 4. Module-owned contracts

Each module defines and maintains its CLI commands and OpenAPI (Swagger) contract, including operation inputs, outputs, and errors. The manager only exposes them.

Each module exposes `GET /<tool-module>/help` with concise descriptions and a
request example for each enabled operation: HTTP method, full path, and JSON
body. Help is maintained by the module, not generated by the manager, and must
not list disabled operations. OpenAPI remains available as the technical contract.

### 5. Module-owned configuration

Each module receives only its configuration object. It provides defaults and validates its fields. It does not locate the global file or inspect how the manager loads it.

Minimize environment variables for individual configuration fields.

### 6. Protected credentials

Credentials are available only where the tool executes. Never include them in responses, logs, packages, or images. Configuration may reference external secret files.

### 7. Generic consumers

Contracts do not assume a specific application, agent, flow, or runtime.

### 8. Independent tests

Each module keeps unit tests for its logic and configuration in its own `tests/` directory. Tests run without the manager or other modules. Do not spend unit-testing effort on mere assembly, registration, or delegation in `module.py`, `cli.py`, and `router.py`.

CLI/HTTP behavior and integration with the manager will be covered by E2E tests, which remain to be defined.

### 9. Namespace packages

Modules use Python namespace packages without `__init__.py` files. Packaging must include these directories. The registration interface lives in `module.py`: `create_module(config, operations)` receives the module configuration and enabled
operations, and returns an instance exposing `register_cli(parser)`, `router`, and `lifespan()` (a synchronous context manager).

## Tool module structure

```text
<tool_module>/
├── module.py         # Module instance factory
├── config.py         # Configuration, defaults, and validation
├── schemas.py        # Inputs, outputs, and errors
├── service.py        # Operation logic
├── cli.py            # CLI commands
├── router.py         # Endpoints and OpenAPI contract
├── docs/
│   └── config.md      # Fields, defaults, minimal/effective JSON
└── tests/
    ├── test_config.py
    └── test_service.py
```

CLI and router call `service.py`. This is the common structure, not an exhaustive
file list: Telegram also has `receiver.py`, `adapters.py`, `help.py` and business
helpers with integration-specific responsibilities.

### `module.py`: module assembly

- `create_module(config, operations)` receives configuration and enabled operations and creates the module instance.
- Delegates validation and defaults to `config.py`.
- Creates the service and shares it with CLI and router.
- Exposes `register_cli(parser)`, `router`, and `lifespan()` for the manager to control, without depending on it.
- Exposes only enabled operations through both CLI and HTTP.
- Contains no business logic and executes no operations during assembly. If no resources need opening or closing, `lifespan()` returns an empty context.
- Module-owned listeners/resources are started and stopped through `lifespan()`.
  Telegram uses this for its separate provider receiver when configured; starting
  that listener does not register a webhook with Telegram. Provider registration
  requires the explicit `start` operation.
- Only `ggets serve` enters module lifespans for the HTTP application lifetime.
  CLI commands call services directly without starting module listeners.

### `cli.py`: command adapter

- `register_cli(parser, service, enabled_operations)` declares commands and arguments without executing operations during registration.
- Each command has an explicitly named handler: `execute_<operation>`.
- The handler validates JSON input through the schemas, calls the service, and converts the result to JSON-serializable data.
- Does not implement business logic, load global configuration, or know the manager.
- Mere registration or delegation requires no unit-testing effort; behavior will be checked through E2E tests.

### `router.py`: HTTP adapter

- `create_router(service, enabled_operations)` declares endpoints and their OpenAPI contract: inputs, outputs, and errors.
- Each endpoint validates input through the schemas, calls the service, and returns a JSON response.
- Consumer API routes are module-relative; the manager adds the `/<tool-module>` prefix.
- Provider ingress may require a separate module-owned listener. Telegram's
  receiver is not exposed through the consumer router/OpenAPI; it validates the
  provider secret independently of the manager API's Bearer token.
- Does not implement business logic, configure the server, or know the manager.
- Route declaration or service delegation requires no unit-testing effort; behavior will be checked through E2E tests.

### `schemas.py`: data contracts

- Defines each operation's inputs, outputs, and errors: types, required fields, and constraints.
- CLI and HTTP share these schemas to maintain the same contract.
- Contains no business logic and does not depend on the manager.
- Do not spend unit-testing effort on schemas.

### `service.py` and `business/`: operation logic

- `service.py` implements operations using the module's schemas and validated configuration, without depending on CLI, HTTP, or the manager.
- If the logic grows, `service.py` becomes a facade delegating to `business/`, which contains business logic only.
- Follow the single-responsibility principle: classes and functions have a specific purpose. Files of 500 lines or more are not accepted.
- Avoid artificial fragmentation: no trivial two-line helpers or classes without their own responsibility.
- Each unit of logic must have isolated unit tests. Dependencies must be naturally replaceable with mocks, without complicated workarounds.

### `config.py`: module configuration

- Defines a plain dataclass without field defaults; optional fields are allowed.
- Declares a complete `DEFAULT_CONFIG` instance. Optional credentials or deployment
  values may default to `None`; defaults need not activate an integration.
- Operations requiring missing configuration must report that explicitly. A
  module may remain available for status/help while not configured.
- The mapper receives only the module's JSON section, extracted by the manager, not the global configuration.
- Validates incoming values: each valid value overrides its corresponding default; missing or invalid values retain the default.
- Does not modify `DEFAULT_CONFIG`: returns a new configuration object.
- Validation and default-application logic is covered by unit tests.

## Scope

These rules describe the target architecture, not a guarantee of current implementation. Integration-specific behavior is documented within each module. Statelessness is not a general requirement.

Manager responsibilities are defined in [tool-manager-rules.md](tool-manager-rules.md).

## Configuration documentation

Each module must include `docs/config.md` listing every configuration field, its purpose, whether it is required, and its default. Use a concise table; document no-configuration modules explicitly.
Include a minimal JSON example with required fields only and its effective configuration after applying defaults.
Distinguish required-for-activation fields from fields with defaults; do not
present Docker-specific listen addresses as application defaults. Document
configuration errors, persistence and any separate listener briefly. The manager's
`server` section is not module configuration.
